# Data Dictionary — YottaFlex AI Lead Scoring

## 1. Purpose

This document explains the CSV datasets generated by the synthetic CRM lead-scoring and sales-pipeline project.

## 2. Core CRM Entities

### Company — `companies.csv`

Represents an organization.

| Field | Description |
|---|---|
| `company_id` | Unique company identifier |
| `company_name` | Company name |
| `industry` | Industry category |
| `employee_count` | Approximate number of employees |
| `territory` | Sales territory |
| `is_customer` | Indicates whether the company is an existing customer |

### Contact — `contacts.csv`

Represents a person associated with a company.

| Field | Description |
|---|---|
| `contact_id` | Unique contact identifier |
| `company_id` | Associated company |
| `first_name` | Contact's first name |
| `last_name` | Contact's last name |
| `job_title` | Contact's job title |

### Lead — `leads.csv`

Represents a potential sales prospect.

| Field | Description |
|---|---|
| `lead_id` | Unique lead identifier |
| `contact_id` | Associated contact |
| `company_id` | Associated company |
| `campaign_id` | Related campaign |
| `source` | Lead source |
| `product` | Product of interest |
| `created_date` | Lead creation date |
| `status` | Current lead status |
| `is_stale` | Indicates whether the lead is considered stale |

### Campaign — `campaigns.csv`

Represents a marketing campaign.

| Field | Description |
|---|---|
| `campaign_id` | Unique campaign identifier |
| `campaign_name` | Campaign name |
| `channel` | Campaign channel |
| `status` | Campaign status |

### Activity — `activities.csv`

Represents an engagement event associated with a lead.

| Field | Description |
|---|---|
| `activity_id` | Unique activity identifier |
| `lead_id` | Associated lead |
| `activity_type` | Type of engagement |
| `activity_date` | Event date |
| `occurred_after_conversion` | Indicates whether the event occurred after conversion |

### Consent — `consents.csv`

Stores a contact's communication preference.

| Field | Description |
|---|---|
| `consent_id` | Unique consent record identifier |
| `contact_id` | Associated contact |
| `channel` | Communication channel |
| `status` | Consent status, such as `OPTED_IN` or `OPTED_OUT` |
| `effective_date` | Date the consent record becomes effective |

### Sales Representative — `sales_reps.csv`

Represents a salesperson and their routing attributes.

| Field | Description |
|---|---|
| `sales_rep_id` | Unique salesperson identifier |
| `sales_rep_name` | Salesperson's name |
| `territory` | Assigned sales territory |
| `product` | Product specialization |
| `active` | Indicates whether the salesperson is active |

### Task — `tasks.csv`

Represents a follow-up task.

| Field | Description |
|---|---|
| `task_id` | Unique task identifier |
| `lead_id` | Associated lead |
| `sales_rep_id` | Assigned salesperson |
| `task_status` | Task status |

### Opportunity — `opportunities.csv`

Represents a sales deal.

| Field | Description |
|---|---|
| `opportunity_id` | Unique opportunity identifier |
| `lead_id` | Associated lead |
| `company_id` | Associated company |
| `sales_rep_id` | Assigned salesperson |
| `product` | Product being considered |
| `amount` | Estimated opportunity amount |
| `stage` | Current sales stage |
| `outcome` | Outcome such as `OPEN`, `WON`, or `LOST` |
| `lost_reason` | Reason recorded for a lost opportunity |

### Stage History — `stage_history.csv`

Tracks an opportunity's sales-stage progression.

| Field | Description |
|---|---|
| `stage_history_id` | Unique stage-history record identifier |
| `opportunity_id` | Associated opportunity |
| `stage` | Stage recorded in the history |
| `sequence` | Position in the stage sequence |

## 3. Derived Pipeline Outputs

### Lead Scores — `lead_scores.csv`

Stores calculated lead scores.

| Field | Description |
|---|---|
| `lead_id` | Scored lead |
| `company_id` | Associated company |
| `fit_score` | Company-fit component |
| `intent_score` | Buying-intent component |
| `engagement_score` | Engagement component |
| `lead_score` | Combined score out of 100 |
| `priority` | `LOW`, `MEDIUM`, or `HIGH` |
| `score_rule_version` | Version of the scoring rules |

### Lead Routing — `lead_routing.csv`

Stores routing decisions for leads.

| Field | Description |
|---|---|
| `lead_id` | Routed lead |
| `company_id` | Associated company |
| `lead_score` | Lead's score |
| `priority` | Lead priority |
| `territory` | Territory used for routing |
| `product` | Product of interest |
| `consent_status` | Consent status considered during routing |
| `sales_rep_id` | Assigned salesperson, if any |
| `routing_status` | Routing outcome |
| `routing_reason` | Explanation for the routing outcome |
| `task_id` | Associated follow-up task, if any |
| `task_status` | Follow-up task status, if any |

## 4. Scoring Logic

The current scoring system combines three components:

| Component | Maximum points |
|---|---:|
| Company fit | 30 |
| Buying intent | 40 |
| Engagement | 30 |
| **Total** | **100** |

Priority categories:

- `LOW`: score from 0 to 39
- `MEDIUM`: score from 40 to 69
- `HIGH`: score from 70 to 100

Refer to `src/scoring.py` for the exact scoring weights.

## 5. Relationships

- A company can have multiple contacts and leads.
- A contact can be associated with multiple leads.
- A campaign can be associated with multiple leads.
- A lead can have multiple activities.
- Consent records refer to contacts and communication channels.
- Leads can have scores, routing decisions, and follow-up tasks.
- Sales representatives can be assigned leads and tasks.
- An opportunity is associated with a lead and company.
- An opportunity can have multiple stage-history records.

## 6. Anomaly and Validation Files

| File | Purpose |
|---|---|
| `anomaly_cases.csv` | Describes anomaly test fixtures |
| `ground_truth.csv` | Stores expected anomaly labels and detection descriptions |
| `validation_summary.csv` | Records structural validation results |

The five anomaly scenarios cover prohibited contact after opt-out, post-conversion activity used in scoring, incorrect territory assignment, duplicate opportunity associations, and missing stage transitions.

The current anomaly detector evaluates fixture descriptions. Additional integration tests are needed to demonstrate detection against altered production records.

## 7. Data Provenance

All generated CRM data is synthetic and intended for development, testing, and analysis. It does not represent actual customers or prospects.
